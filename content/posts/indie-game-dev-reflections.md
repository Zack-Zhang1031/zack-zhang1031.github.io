这篇不是技术教程，更像一篇阶段性自述。从写 Python 学习笔记到在 CrazyGames 上发布游戏，我的路线不算"标准"——没上过游戏开发课，也没在大厂做过项目。但正因如此，踩过的坑和想明白的事也许对同样"半路出家"的人有参考价值。

---

## 一、我是怎么开始做独立游戏的

### 从 Python/OpenCV 到游戏开发的转折

我的编程起点是 Python，最早是拿 OpenCV 做一些图像处理的实验和课程项目。写算法题、跑数据、训练模型，这些事做多了会有一种"我到底在做什么"的虚无感——代码跑完输出一个准确率数字，没有人会去"玩"它。

转折发生在一次算法竞赛结束后。我想做个"别人能玩、能笑、能骂"的东西，而不是又一篇跑在 Jupyter Notebook 里的 demo。游戏天然就是这个载体：有交互、有反馈、有目标，而且最关键的是——可以分享一个链接，对方点开就能体验。

选定游戏这个方向后，我没有立刻去啃《游戏引擎架构》这种大厚书。我用 Python 写了个用 `pygame` 拼起来的打砖块原型，花了两个晚上。从那一刻起我意识到，做游戏并不需要先把所有理论学完，它更像是一种"边做边学"的活。

### 为什么选 Cocos Creator 而不是 Unity

很多人问我：既然要做游戏，为什么不直接上 Unity？说实话，这个问题我后来做《修仙 Roguelike》时才反过来看清楚。当时选 Cocos Creator 有几个很现实的原因：

| 维度 | Cocos Creator | Unity |
|---|---|---|
| 学习曲线 | 低，TypeScript 上手快 | 中等，C# + 编辑器概念多 |
| 包体大小 | 小，适合 Web | 偏大，Web 导出有坑 |
| CrazyGames 兼容性 | 原生 HTML5，几乎零成本 | 需 WebGL build + 体积优化 |
| 生态与资源 | 2D 休闲足够用 | 全场景，但学习负担重 |
| 上手到出第一个游戏 | 周末即可 | 至少 2-3 周 |

我当时目标很明确：在 CrazyGames 这种 Web 平台发布休闲小游戏。Cocos Creator 的 TypeScript 对一个写过 Python 的人几乎零门槛，HTML5 导出是原生能力，包体小、加载快，正好契合休闲游戏"点开就玩"的属性。Unity 直到后来我想做更重的 Roguelike（需要 ECS、DOTS 思路、更复杂的实体管理）才提上日程。

一句话：**引擎选择服从于项目目标，而不是反过来**。

### 第一个项目《数钱》的诞生

《数钱》的核心玩法很简单：屏幕上飞过钞票，玩家在限定时间内点数，数对了得分。这个原型我用了大概一个周末两天就跑通了——一个场景、一个计时器、一个点击响应、一个分数累加，加起来不到 300 行 TypeScript。

但"原型能跑"和"能发布"之间隔着一个我后来才体会到的鸿沟。接下来的几周我都在打磨：

- 音效反馈（点对了"叮"一声，点错了"嗡"一声）
- 钞票飞入飞出的缓动动画
- 分数飘字、连击高亮
- 主菜单、暂停、结算页的 UI 流转
- CrazyGames 的 SDK 接入（广告、计分榜）

这些"看起来不核心"的东西，往往占用 70% 以上的时间。这也是我第一次理解为什么圈内常说"做完 demo 只完成了 20%"。

## 二、技术栈与学习路线

### 当前技术栈全景

经过这段时间的积累，我手上的技术栈大致是这样的：

```
┌─────────────────────────────────────────────┐
│  休闲游戏 (CrazyGames)                       │
│  Cocos Creator + TypeScript + HTML5          │
├─────────────────────────────────────────────┤
│  修仙 Roguelike (本地/桌面)                   │
│  Unity 6 + C# + ECS 思路                     │
├─────────────────────────────────────────────┤
│  AI 与算法辅助                                │
│  Python + OpenCV + PyTorch (兴趣 + 工具链)    │
└─────────────────────────────────────────────┘
```

我并没有刻意"集齐"这套组合，而是每个工具都是在某个具体项目里被需要才学的。TypeScript 是因为 Cocos，C# 是因为 Unity，Python 一直是我的"算法笔记本"和写小工具的首选（比如批量处理素材、跑数据脚本）。

### 学习顺序建议

如果让我给同样半路出家的人排一条路线，我会这样写：

1. **编程基础**（任意一门语言，能写循环、函数、理解类型即可）
2. **引擎入门**（跟着官方教程做一个 Hello World 级别的小游戏）
3. **做一个最小可玩游戏**（MVP：一个核心玩法能闭环）
4. **发布**（哪怕只是扔到 itch.io 或 CrazyGames，走完一次完整流程）
5. **迭代**（根据真实玩家反馈调整）

这里最关键的是第 3 步和第 4 步之间不要停下来。"做完美"是后面的事，先把闭环走通，你才会知道真正的难点在哪。很多人卡在"教程地狱"里半年，一个能玩的东西都没发布过。

### 哪些知识"看起来没用但其实很关键"

游戏开发里有几门"老掉牙"的计算机基础课，我做项目时反复用到：

- **数据结构**：尤其是状态机（FSM）。游戏里的角色状态、UI 流转、关卡进度，几乎都是状态机。不会画状态图，代码很快就会变成一堆 `if-else` 的意大利面。
- **线性代数**：变换矩阵、向量点乘叉乘。休闲游戏里看似用不到，但只要你做任何"平滑跟随""抛物线""屏幕震动"，背后全是向量运算。
- **设计模式**：对象池（Object Pool）几乎是所有"频繁生成销毁"场景的标配；观察者模式（Observer）是解耦 UI 和逻辑的利器。

举个最直白的例子，《捡钱》里金币、红包、炸弹会持续生成销毁，不做对象池的话帧率会肉眼可见地抖。下面这段是我在 Cocos 里用过的简化版对象池：

```typescript
export class ObjectPool<T extends cc.Node> {
    private pool: T[] = [];
    private prefab: cc.Prefab;

    constructor(prefab: cc.Prefab) {
        this.prefab = prefab;
    }

    acquire(parent: cc.Node): T {
        let node = this.pool.pop();
        if (!node) {
            node = cc.instantiate(this.prefab) as T;
        }
        node.parent = parent;
        node.active = true;
        return node;
    }

    release(node: T): void {
        node.active = false;
        node.parent = null;
        this.pool.push(node);
    }
}
```

这种"看似理论"的东西，实际项目里每天都在用。

## 三、时间管理与项目节奏

### 业余开发的现实约束

我得承认，我并不是全职做游戏。学业/工作占掉白天的大头，留给游戏的时间通常是晚上 1-2 小时，周末能多挤出 3-4 小时。一周下来有效开发时间大概 10-15 小时。

这种时间预算决定了所有决策：不能做需要长期沉浸才能推进的重型项目，不能依赖"等周末一次性写 8 小时"的幻想（会被打断），必须把任务切得足够小，小到哪怕只有 30 分钟也能往前推一步。

### milestone 驱动开发

我后来摸索出的一套办法是 **milestone 驱动**。每个项目拆成 M0 到 M7 若干个里程碑，每个里程碑有明确的验收标准，写在一个 markdown 文件里。比如《捡钱》的里程碑大致是：

| Milestone | 内容 | 验收标准 |
|---|---|---|
| M0 | 核心玩法原型 | 能接到金币得分，漏掉扣分 |
| M1 | 美术与音效接入 | 视听闭环，不再用占位图 |
| M2 | 完整游戏循环 | 主菜单 → 游戏 → 结算 → 重开 |
| M3 | 难度曲线初版 | 5 分钟内有明显难度递增 |
| M4 | CrazyGames SDK 接入 | 广告、排行榜、分享可用 |
| M5 | 内部测试 | 3 个朋友通关，无致命 bug |
| M6 | 上线 | 通过审核，公开可玩 |
| M7 | 上线后迭代 | 根据数据调一轮难度 |

每个 milestone 我会预估一个时间（通常 1-2 周），到点没完成就评估是砍范围还是延期。这个表格最大的价值不是"计划得多准"，而是**让我随时知道自己在哪一步、离上线还有多远**。

### 怎么判断一个项目该继续还是该砍

这是业余开发者最难的决策之一。我的经验法则是：**给每个项目设一条 2 周止损线**。

如果两周后核心玩法还没"好玩"起来——不是"完美"，是"好玩"——基本就可以判断这个方向有问题，继续投入只是沉没成本。《数钱》的原型第一个周末就让我自己上瘾了，所以我知道它值得继续。我后来砍掉过两个项目：一个塔防、一个解谜，都是在两周节点上诚实地承认"自己都不想玩"，果断停手。

砍项目不丢人，**死磕一个不好玩的项目才是真浪费**。

## 四、心态：接受不完美

### 完美主义是最大的敌人

我以前是典型的完美主义者：写代码要重构三遍，美术要调到像素级，UI 动画要丝滑到 120fps。结果是——半年过去，一个游戏都没发布。

后来我逼自己接受一个事实：**"做完"比"做好"更重要**。一个 70 分但发布了的游戏，比一个 95 分但永远躺在硬盘里的游戏有价值得多。发布意味着有真实玩家、有真实反馈、有真实的"下一次做得更好"的起点。

我现在给每个项目定一个"够用就行"的标准：

- 美术：风格统一即可，不追求大作级别
- 代码：能跑、能维护即可，不追求架构完美
- 玩法：核心闭环好玩即可，不追求内容海量

剩下的留给迭代。上线后的真实数据会告诉你哪里值得花时间，而不是你自己脑补哪里"应该"完美。

### 怎么处理发布后的负面反馈

《数钱》上线后收到的第一个差评是："太简单了，玩两分钟就腻。" 当时心里确实有点堵，但冷静下来想，对方说的是事实。我的应对是加了一个**计时模式**：在原本的休闲点数基础上，引入 30 秒倒计时和连击奖励，难度曲线立刻陡了起来。

这件事让我学到几条：

1. **负面反馈是免费的用研**。玩家花时间骂你，说明他还在意。
2. **不要急着反驳或解释**。先理解他为什么这么觉得。
3. **能快速迭代就快速迭代**。难度模式我在一周内就上了线。
4. **保留原版**。差评不代表所有玩家都想要更难，给选择比改掉更好。

## 五、对想入坑的人的建议

如果你也是半路出家、想试试做独立游戏，下面这几条是我最想说的：

1. **先做最小的可玩游戏**。一个场景、一个机制、一个目标，能玩通就发。别想着第一作就是精品。
2. **不要一上来就做大型 RPG**。开放世界、剧情分支、装备系统……这些每一个都是独立的工程难题。先用休闲游戏把"完整流程"跑通。
3. **善用 AI 辅助但不要依赖**。我用 AI 帮我查 API、生成样板代码、debug 报错，但**核心玩法设计和架构决策永远自己拿**。AI 写出来的代码你不理解，上线出 bug 你会修不出来。
4. **找到同温层**。社区（Cocos 论坛、Unity 官方社群、独立开发者 Discord）、B 站发开发日志、GitHub 开源小项目——孤独是业余开发最大的敌人，被人看见本身就是动力。
5. **接受自己的节奏**。别拿自己和全职独立开发者比进度，你只要持续往前走就行。

## 六、下一步计划

接下来一段时间，我的打算大致是这样：

- **短期**：丰富《数钱》《捡钱》的内容。加新玩法模式、节日主题皮肤、成就系统，让老游戏有长尾。
- **中期**：尝试新玩法。我对 Roguelike + 卡牌的混合机制很感兴趣，可能会用 Unity 6 做一个小体量的原型，验证一下手感。
- **长期**：探索变现路径。CrazyGames 的广告分成、可能的内购设计、是否做手游版本——这些都是需要数据支撑才能下的决策，不急。

我并不打算短期内全职做独立游戏。现实地说，业余开发反而让我更自由——不用靠游戏吃饭，所以可以挑自己感兴趣的方向做。这种状态对我来说是舒服的。

---

最后一句送给同样在路上的人：**做游戏是一场马拉松，不是冲刺。今天写一行代码，明天调一个数值，慢慢就长出来了。** 共勉。
