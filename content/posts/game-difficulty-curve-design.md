做休闲游戏最容易忽略的不是代码，而是难度曲线——前 30 秒太无聊玩家就走，第 2 分钟太难玩家就弃。这篇笔记从心流理论出发，结合《捡钱》《数钱》的实际调表过程，聊聊怎么让玩家"刚好想再来一局"。

---

## 一、心流理论与难度曲线的关系

### 心流是什么

心流（Flow）是心理学家 Mihaly Csikszentmihalyi 提出的概念，指的是人在"挑战与能力刚好匹配"时会进入的那种全神贯注、忘记时间的状态。它的核心可以用一张经典的二维图来理解：

| 能力 \ 挑战 | 低挑战 | 高挑战 |
|---|---|---|
| **高能力** | 无聊（Boredom） | 心流（Flow） |
| **低能力** | 冷漠（Apathy） | 焦虑（Anxiety） |

游戏设计的目标，就是让玩家尽可能长时间停留在右下→右上这条对角线上：随着玩家能力提升，挑战也同步抬升，两者始终咬合。

### 休闲游戏的理想曲线

对于 CrazyGames 这类平台的休闲游戏，玩家没有耐心读说明，点开就玩。我把理想曲线拆成几个阶段：

```
难度
 ↑
 │              ┌──── 高潮 + 失败点
 │           ╱─┘
 │        ╱─┘   ← 难度攀升
 │     ╱─┘
 │  ╱─┘  ← 进入心流
 │─┘  ← 低门槛教学
 └──────────────────────→ 时间
   0s   30s   2min   5min
```

- **0-30 秒**：低门槛教学。只给最基础的元素，让玩家"我先试试"。
- **30 秒-2 分钟**：进入心流。引入机制变化（新元素、新规则），但难度仍可控。
- **2-5 分钟**：难度攀升。速度、频率、惩罚力度都开始上抬。
- **5 分钟+**：失败点。绝大多数休闲玩家在 3-5 分钟内会失败，而失败时机的关键是"差一点点就成功"，激发再来一局的冲动。

### 不同品类的曲线差异

不同游戏类型的曲线形状差别很大：

| 类型 | 典型曲线 | 失败后果 | 目标时长 |
|---|---|---|---|
| 超休闲（Hyper-casual） | 陡峭指数上升，30 秒见分晓 | 立即重来 | 1-3 分钟 |
| 街机（Arcade） | 阶梯式加速，每波后微缓冲 | 重来或续命 | 3-10 分钟 |
| 中度（Mid-core） | 缓慢线性，配合内容解锁 | 损失进度 | 10-30 分钟 |

《捡钱》是街机型，《数钱》更偏超休闲。两者的曲线设计思路完全不同——《捡钱》靠阶梯加速制造紧张感，《数钱》靠计时模式把"无压力点数"变成"限时挑战"。

## 二、数值设计的基础框架

### 核心变量定义

不管什么品类，休闲游戏的难度最终都能拆成几个可调变量：

- **速度（Speed）**：物体移动速度，比如金币下落速度
- **频率（Frequency）**：物体生成间隔，比如每 0.5 秒生成一个
- **分数权重（Score Weight）**：不同元素的得分/扣分比例
- **惩罚力度（Penalty）**：失误的代价，比如漏一个金币扣 1 命 vs 扣 3 命
- **元素复杂度（Complexity）**：同时存在的元素种类数量

调表的本质，就是在时间轴上调整这几个变量的取值。

### 增长曲线对比

变量随时间怎么涨，有三种常见模式：

| 增长方式 | 公式形态 | 适用场景 | 风险 |
|---|---|---|---|
| 线性增长 | `v = v0 + k*t` | 中度游戏、长局 | 后期太缓、无聊 |
| 指数增长 | `v = v0 * a^t` | 超休闲、短局 | 后期失控、不可玩 |
| 阶梯增长 | `v = v0 + k*floor(t/Δ)` | 街机、波次制 | 阶梯间突变需缓冲 |

我的经验是：**街机游戏用阶梯增长最稳**。它既有明确的"波次感"（玩家能感知到"这一波变难了"），又不会像指数增长那样在后期突然崩盘。

### 《捡钱》的数值表设计实例

下面是《捡钱》实际用过的一版数值表，给出具体的速度、频率、分数配置：

| 时间段 | 下落速度 (px/s) | 生成间隔 (ms) | 可生成元素 | 分数权重 | 备注 |
|---|---|---|---|---|---|
| 0-10s | 300 | 800 | 仅金币 | 金币 +10 | 慢速教学 |
| 10-30s | 360 (+20%) | 700 | 金币 + 红包 | 红包 +50 | 引入高分元素 |
| 30-60s | 450 (+50%) | 600 | 金币 + 红包 + 炸弹 | 炸弹 -30 | 引入惩罚 |
| 60-75s | 540 | 550 | 全元素 | 同上 | 第一波加速 |
| 75-90s | 630 | 500 | 全元素 | 同上 | 第二波加速 |
| 90s+ | 每 15s +90 | 每 15s -50 | 全元素 | 同上 | 持续攀升 |

这版表的设计思路有三点：

1. **前 10 秒只有金币**。新手不会一上来就被炸弹惩罚，先建立"这游戏很简单"的安全感。
2. **机制变化先于数值变化**。10 秒和 30 秒引入的不是更快的金币，而是新元素（红包、炸弹），让"变难"来自机制而非单纯数值堆砌。
3. **60 秒后才开始阶梯加速**。前期靠机制，后期靠数值，避免玩家过早进入"只会越来越快"的疲劳期。

对应的 TypeScript 配置代码大致长这样：

```typescript
interface PhaseConfig {
    startTime: number;        // 该阶段开始时间（秒）
    speed: number;            // 下落速度 px/s
    spawnInterval: number;    // 生成间隔 ms
    elements: ElementType[];  // 可生成元素
    scoreWeights: Record<ElementType, number>;
}

enum ElementType {
    Coin = "coin",
    RedPacket = "redPacket",
    Bomb = "bomb",
}

const DIFFICULTY_TABLE: PhaseConfig[] = [
    {
        startTime: 0,
        speed: 300,
        spawnInterval: 800,
        elements: [ElementType.Coin],
        scoreWeights: { coin: 10, redPacket: 0, bomb: 0 },
    },
    {
        startTime: 10,
        speed: 360,
        spawnInterval: 700,
        elements: [ElementType.Coin, ElementType.RedPacket],
        scoreWeights: { coin: 10, redPacket: 50, bomb: 0 },
    },
    {
        startTime: 30,
        speed: 450,
        spawnInterval: 600,
        elements: [ElementType.Coin, ElementType.RedPacket, ElementType.Bomb],
        scoreWeights: { coin: 10, redPacket: 50, bomb: -30 },
    },
    {
        startTime: 60,
        speed: 540,
        spawnInterval: 550,
        elements: [ElementType.Coin, ElementType.RedPacket, ElementType.Bomb],
        scoreWeights: { coin: 10, redPacket: 50, bomb: -30 },
    },
    // 90 秒后用动态计算
];

// 90 秒后的阶梯加速
function getDynamicSpeed(elapsed: number): number {
    const baseSpeed = 630;
    const step = Math.floor((elapsed - 90) / 15);
    return baseSpeed + step * 90;
}

function getCurrentPhase(elapsed: number): PhaseConfig {
    // 90 秒前查表
    for (let i = DIFFICULTY_TABLE.length - 1; i >= 0; i--) {
        if (elapsed >= DIFFICULTY_TABLE[i].startTime) {
            return DIFFICULTY_TABLE[i];
        }
    }
    return DIFFICULTY_TABLE[0];
}
```

把数值从代码里抽出来做成数据表的好处是：调表时改数字就行，不用动逻辑；后续做 A/B 测试也方便替换整张表。

## 三、玩家分层与自适应难度

### 休闲游戏需要分层吗

需要，但要克制。轻度玩家想要"5 分钟爽一把"，核心玩家想要"挑战极限分数"。两者的需求其实是冲突的——给前者简单，后者嫌无聊；给后者难，前者直接走人。

我的做法是**显式分层**，而不是"一刀切"：

- **休闲模式**：曲线平缓，失败不扣命，主打放松
- **计时模式**：固定时长，比谁分数高，给轻度玩家一点压力
- **极限模式**：起始难度直接拉到 60 秒后的水平，给核心玩家

把选择权交给玩家，比偷偷调整难度更诚实，也更不容易被骂"暗改"。

### 基于行为数据的难度调整

除了显式分层，还可以做隐式的自适应难度（Dynamic Difficulty Adjustment, DDA）。核心思路是**监控玩家行为，发现他快撑不住时偷偷降速**。

我监控的几个信号：

- **连击数**：连续接住多少个，反映当前手感
- **近期失败率**：最近 10 秒漏掉/失误的比例
- **生命值变化**：是否在快速掉血

逻辑大致是：

```typescript
function adjustDifficulty(player: PlayerState, phase: PhaseConfig): PhaseConfig {
    const adjusted = { ...phase };

    // 玩家连续失误：降速 10%，延长间隔 10%
    if (player.recentMissRate > 0.5) {
        adjusted.speed *= 0.9;
        adjusted.spawnInterval *= 1.1;
    }
    // 玩家连击爆表：提速 5%，缩短间隔 5%
    else if (player.combo > 15) {
        adjusted.speed *= 1.05;
        adjusted.spawnInterval *= 0.95;
    }

    return adjusted;
}
```

注意几个原则：

1. **调整幅度要小**。一次性降 30% 玩家会立刻察觉，反而出戏。
2. **不要让玩家发现**。DDA 一旦被察觉，"成就感"就崩了——玩家会觉得自己被施舍。
3. **设上下限**。无论怎么调整，都不能超过当前阶段 ±15% 的范围，否则曲线会乱。

### 何时给"喘息"、何时上压力

街机游戏有个不成文的节奏：**每波高潮后给 2 秒缓冲**。

《捡钱》里我做了这样一个机制——每次难度阶梯切换时（比如 60 秒、75 秒、90 秒的加速点），先来一波"密集高潮"（生成间隔瞬间缩短到 300ms，持续 2 秒），然后立刻进入 2 秒的"空白喘息"（生成间隔拉到 1000ms，只出金币不出炸弹），再恢复正常节奏。

这种"紧张-释放"的呼吸感，是让玩家愿意再来一局的关键。一直紧绷会让玩家疲劳放弃，一直松垮会让玩家无聊退出。

## 四、调表的实操流程

### 怎么收集玩家数据

调表不能靠拍脑袋，得有数据。我的数据来源分三层：

1. **自己玩**：最廉价，但样本偏差大。开发者对自己游戏太熟，测出来的难度永远偏低。我会刻意"假装不会玩"来模拟新手，但这只能做粗调。
2. **朋友测试**：找 3-5 个不玩游戏的朋友当面玩，观察他们在哪里卡住、哪里皱眉、哪里放下手机。这种定性观察比任何埋点都有用——你能直接看到情绪。
3. **上线后埋点**：在游戏里加简单的事件上报，记录每个时间段的失败率、平均存活时长、重玩率。CrazyGames 这种 Web 平台可以直接用 `localStorage` 存档，再用一个简单的 fetch 上报到自己的小服务。

埋点要采集的关键指标：

| 指标 | 含义 | 用途 |
|---|---|---|
| 存活时长分布 | 每局玩了多少秒 | 判断整体难度是否合适 |
| 各时间段失败率 | 哪个时间段死的人最多 | 定位"难度跳崖"点 |
| 重玩率 | 一局结束后是否立刻重开 | 判断"再来一局"的吸引力 |
| 首次失败时机 | 新手第一次死在第几秒 | 评估新手引导 |

### A/B 测试在休闲游戏中的应用

上线后，如果数据不足以支撑决策，就上 A/B 测试。做法很简单：随机把玩家分成两组，加载不同的难度配置表，对比留存和重玩率。

```typescript
function loadDifficultyTable(): PhaseConfig[] {
    const variant = Math.random() < 0.5 ? "A" : "B";
    // 上报分组
    reportEvent("ab_assign", { variant });

    return variant === "A"
        ? DIFFICULTY_TABLE_V1  // 原版
        : DIFFICULTY_TABLE_V2; // 调整版
}
```

A/B 测试有几个坑要注意：

- **样本量要够**。休闲游戏日活不大时，A/B 跑一周可能都不显著，别急着下结论。
- **只改一个变量**。同时改速度和频率，你不知道哪个起作用。
- **看长期留存而非短期指标**。难度调低会让"单局时长"变长，但长期留存可能反而下降——玩家太快通关就没动力回来。

### 《数钱》调表的 3 次迭代复盘

《数钱》的难度我前后调了三轮，每一轮都对应一次上线后的反馈：

**V1：太简单。**
最初版本没有计时，玩家可以无限点下去，玩 5 分钟就腻。数据上看，平均单局时长超过 8 分钟，但重玩率只有 12%——典型的"无聊型长局"。

**V2：加计时模式。**
引入 60 秒倒计时，单局时长压到 1-2 分钟，重玩率涨到 35%。但新的反馈来了："太赶了，根本来不及数。" 失败率在 30 秒后陡升，说明难度曲线在 30 秒处有跳崖。

**V3：加连击奖励 + 平滑曲线。**
重新设计曲线：30 秒前速度保持不变，30-50 秒线性上升，50 秒后才进入加速。同时引入连击奖励——连续数对 5 次额外加 2 秒时间。这让"高手"能延长游戏，"新手"也不会被瞬间压垮。

最终版本的重玩率稳定在 48%，平均单局 2 分 20 秒——这个数据我满意了。整个调表过程让我深刻体会到：**难度曲线不是设计出来的，是调出来的**。

## 五、常见设计误区

最后总结几个我踩过或见过的坑：

1. **难度跳崖**。某个时间点难度突然飙升，玩家毫无准备地死掉。原因通常是阶梯增长的"阶梯"太大。解决：每个阶梯之间加过渡段，或限制单次提速幅度不超过 20%。

2. **纯靠数值堆砌而非机制变化**。从第 1 秒到第 5 分钟，只是速度越来越快、生成越来越密，玩家很快就会疲劳。正确做法是定期引入新机制（新元素、新规则、新目标），让"变难"来自"变复杂"而非"变快"。

3. **忽略新手引导的难度**。新手引导本身就是一段难度曲线——太快玩家学不会，太慢玩家嫌啰嗦。我的经验是引导段不超过 10 秒，且引导期间**绝对不能让玩家失败**，否则第一印象就崩了。

4. **调表只调不测**。在编辑器里玩 100 遍，不如找 3 个真人玩 1 遍。开发者对自己游戏的耐受度远高于真实玩家，自己测出来的难度永远偏高。

5. **迷信"科学调表"**。网上有很多"难度曲线公式"看起来很专业，但游戏是给人玩的，不是给公式算的。公式是起点，体感才是终点。最终标准只有一个：**玩家失败后想不想再来一局**。
