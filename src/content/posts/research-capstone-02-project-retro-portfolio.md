应用能跑了，但"东西做出来了"和"讲清楚它为什么这样做"之间还差一次正式的复盘。这一课做两件事：对案例平台做完整的技术复盘，以及把复盘改写成作品集叙事。前者是给自己和团队的工程档案，后者是给面试官的能力证明。同一份素材，两种文体。

> 前置阅读：全部前 25 课。复盘方法论见 [研究方法](/posts/research-methods-ai/)；写作风格参考本站 [RAG 项目复盘](/posts/rag-project-retrospective/)。

## 复盘的第一块：架构总览与决策回顾

先把系统画在一张图上（这也是 README 和面试白板题的同一张图）：

```
数据源（arXiv / OpenAlex / Crossref / 会议网页）
    ↓ 采集器（API + Scrapy/Playwright，断点续传）
data/raw（快照，只读）
    ↓ 清洗归一化（实体对齐 + 质量门）
data/cleaned（Parquet 分区，M1 数据集版本化）
    ↓ 特征与理解流水线（GROBID / Embedding / 图表抽取）
data/features（融合向量，M3）
    ↓                            ↓
经典模型（M2 分类器）      PostgreSQL + pgvector（M4 底座）
                                ↓
                    FastAPI（检索/分类/统计）
                                ↓
        Streamlit 应用（演示） + Prefect（每日增量）
```

图之外，复盘的核心内容是**关键决策的"为什么"**。挑出整个项目里最重要的六个决策，每个按"当时的选项 → 选择的理由 → 事后的验证"三段写：

1. **以 OpenAlex 为主干数据源**（选项：arXiv 全文优先 / 多源并行）。理由：引用与机构关系最全、API 稳定。验证：Crossref 交叉校验时发现字段一致性高，主干选择正确。
2. **文件层 → 数据库的两阶段存储**（选项：直接上数据库）。理由：分析期文件层更灵活，服务化时才需要数据库。验证：[系列五迁移](/posts/research-data-mgmt-01-postgres-pgvector/) 平滑，没有返工。
3. **Embedding+LR 作为线上分类方案**而非微调 Transformer（见 [系列四对比表](/posts/research-mm-03-deep-text-models/)）。理由：3 个点 F1 的差距换不来 GPU 运维成本。验证：上线后推理延迟达标。
4. **融合策略的消融驱动**（选项：直接堆全文）。理由：[消融实验](/posts/research-mm-05-multimodal-fusion/) 证明全文稀释语义。验证：标题+摘要+图注的配置在评测集上最优。
5. **GROBID 而非自研 PDF 解析**。理由：版面重建是专门的难题，不重复造轮子。验证：主流模板完整率 95%+，扫描版分流 OCR。
6. **Prefect 而非 cron**。理由：[自动化篇的决策框架](/posts/ai-automation-workflow/)——需要 task 级重试与状态面板。验证：增量管线故障恢复时间从小时级降到分钟级。

注意每个决策都带"事后验证"——**没有验证环节的决策回顾只是回忆录，有验证的才是工程复盘**。

## 复盘的第二块：用数据说话

复盘里所有"做得好/不好"都要落成数字。把散落在各课实验记录里的关键指标收拢成一张总表：

| 维度 | 指标 | 数值 | 出处 |
|---|---|---|---|
| 数据规模 | 收录论文数 | 48.7 万 | M1 `_meta.json` |
| 数据质量 | 主键重复率 / 标题缺失率 | 0% / 0.02% | M1 质量门 |
| 分类 | 宏 F1（封存测试集） | 0.812 ± 0.006（LR 基线）/ 0.85+（Embedding+LR） | M2/系列四 |
| 检索 | Recall@10 | 0.83（融合表示）vs 0.79（纯文本） | 系列四评测 |
| 全文解析 | 字段完整率 | 95%+（主流模板） | M3 |
| 服务 | 检索 P95 延迟 | <800ms | M4 压测 |
| 自动化 | 日增量处理耗时 | ~25 min | Prefect 运行记录 |

这张表的价值在系列六第 3 课会再兑现一次：简历上的项目描述和面试里的回答，全部从这张表取数——**数字只有一个出处，杜绝"简历上写的和面试说的对不上"**。

## 复盘的第三块：失败与局限清单

诚实的局限清单是复盘里最增值的部分（[研究方法](/posts/research-methods-ai/)：负面结果是最被低估的产出）。案例平台的已知局限：

- **扫描版 PDF 未覆盖**（需 OCR 支线，评估后 ROI 不足，放弃）。
- **引用网络只存了边表**，没有做图算法分析（PageRank 社群发现是明确的下一步）。
- **分类器在相邻领域（cs.CL/cs.LG）上的混淆**是任务定义问题，多标签化是改进路径，当前版本选择诚实暴露置信度。
- **主题地图的周级更新**意味着新论文的主题归属有延迟。
- **评测集只有 20 个查询**——检索指标的统计功效有限，这是个人项目的资源约束，写出来比藏着强。

每条局限配"为什么没做 + 如果做该怎么做"。面试官追问"项目有什么不足"时，这份清单就是你的答案——主动暴露的局限是自信，被问出来的才是破绽。

## 从复盘到作品集：叙事框架

技术复盘按系统写，作品集叙事按**能力**写。把 24 课的产出重组进一个四段框架：

**第一段：问题与约束**（30 秒版）。"我建了一个科研论文的智能管理与分析平台：从公开 API 和网页采集 48.7 万篇论文元数据，做语义检索、领域自动分类和研究趋势分析。约束是个人项目、零预算、单机 GPU。"

**第二段：架构与决策**（3 分钟版）。架构图 + 挑 2-3 个最有讨论价值的决策展开（推荐：Embedding+LR vs 微调的选型、融合策略的消融实验）。决策的"为什么"比"是什么"重要——这展示的是判断力。

**第三段：数字与证据**。上面那张指标表，加上最有故事性的一个发现（比如 EDA 时通过趋势图断点发现采集管道缺数据的案例）。

**第四段：局限与下一步**。局限清单 + 明确的演进方向。这段的存在让前三段的可信度整体上升。

同一框架也直接产出书面材料：GitHub README（第二段的展开版）、博客文章（本课程 27 篇本身就是）、简历项目描述（第一段的压缩版）。

## 复盘文档的组织与归档

复盘文档进项目仓库 `docs/retrospective.md`，与代码同版本管理。内容结构：架构图、决策记录（ADR 风格）、指标总表、局限清单、演进路线。它不是写完就封存的——每个后续里程碑都回来增补，复盘是活的文档。

## 踩坑排查（复盘环节的坑）

| 症状 | 原因 | 处理 |
|---|---|---|
| 复盘时找不到当时的数字 | 实验记录没归档 | 各课的实验纪律就是为此；缺失的如实标注 |
| 决策理由想不起来 | 决策当时没记录 | 复盘补写时标注"事后重建"，以后决策当时写 ADR |
| 局限清单写成自我表扬 | "缺点是太追求完美"式套路 | 每条局限必须可验证、配改进路径 |
| 指标表各处数字打架 | 没有单一出处 | 总表收拢，所有对外材料从这里取数 |
| 叙事全是技术没有观众 | 没回答"谁在乎" | 每个决策绑定一个业务/用户体验后果 |

## 练习

1. 画出你项目的架构图，标注每个组件对应的里程碑。
2. 写 6 条架构决策记录，每条严格按"选项→理由→验证"三段。
3. 收拢指标总表，找出两个数字出处不一致的地方并修正。
4. 写 5 条局限，每条配"为什么没做"和"怎么做"。

## 面试常问

**Q：复盘和总结的区别？**
总结罗列做了什么；复盘追问决策为什么、结果是否验证、教训是什么。复盘的标志物是决策记录、验证证据和诚实的局限清单——三者缺一就是总结。

**Q：怎么证明项目是你自己做的？**
细节密度：能讲清某个决策当时的备选方案、能背出关键指标及其置信区间、能说出失败样本的具体样子。背出来的项目经不住"为什么不用 X"的追问，自己做的项目每个决策都有来路。

**Q：项目里最大的技术挑战是什么（怎么答）？**
别答"调通某个库"。答有决策含量的：比如"多源数据实体对齐——DOI 覆盖率不足，设计了强弱两档匹配规则并用抽样验证精确率"，或者"融合策略的选择——做了消融实验证明全文反而有害"。挑战的价值在于展示你解决问题的方法论。

**Q：局限清单在面试里怎么用？**
主动在"下一步计划"里讲：它不是认怂，是展示你对系统的理解深度（知道边界在哪）和演进判断力（知道哪步先做）。被问"有什么不足"时直接命中准备过的答案。
